# 상대시간 기반 크롤링 모니터링 테스트 요구사항 문서

## 1. 문서 목적

본 문서는 테이블 내 각 행에 표시되는 **상대시간 UI(예: n초 전 / n분 전 / n시간 전)** 를 기준으로, 크롤링/갱신 상태를 **Playwright 기반 E2E 테스트**로 검증하기 위한 요구사항을 정의한다.

본 테스트는 두 가지 목적을 가진다.

* **CI 테스트**: 기능 및 UI 로직이 깨지지 않았는지 검증
* **주기적 모니터링 테스트**: 실제 운영 환경에서 데이터가 정상적으로 갱신되고 있는지 감시

---

## 2. 테스트 대상 범위

### 2.1 테스트 대상 UI

* 테이블 형태의 리스트 UI
* 각 행(row)은 하나의 크롤링 결과 또는 데이터 엔트리를 의미함
* 각 행에는 다음 정보가 포함됨

    * 절대 시간 기준의 크롤링 시각
    * 해당 시각을 기준으로 계산된 상대시간 문자열

### 2.2 HTML / DOM 요구사항

각 테이블 행은 아래 속성을 반드시 포함해야 한다.

```html
<tr
  data-testid="crawl-row"
  data-row-id="{unique-id}"
  data-crawled-at="1707557400000"
>
  <td class="relative-time">5분 전</td>
</tr>
```

| 속성명                     | 설명                          | 필수 여부 |
| ----------------------- | --------------------------- | ----- |
| data-testid="crawl-row" | Playwright 테스트용 식별자         | 필수    |
| data-row-id             | 행의 고유 식별자                   | 권장    |
| data-crawled-at         | 크롤링 시각 (Unix timestamp, ms) | 필수    |
| .relative-time          | 상대시간 표시 영역                  | 필수    |

---

## 3. 상대시간 UI 요구사항

### 3.1 상대시간 계산 기준

* 기준 시간(now)은 클라이언트 시간(Date.now())을 사용한다.
* 상대시간은 data-crawled-at 값을 기준으로 계산한다.

### 3.2 표시 규칙

| 시간 차이 | 표시 형식 |
| ----- | ----- |
| < 60초 | n초 전  |
| < 60분 | n분 전  |
| ≥ 60분 | n시간 전 |

* 숫자의 정확한 일치는 테스트 대상이 아니다.
* 단위(초/분/시간)의 논리적 일관성만 보장하면 된다.

---

## 4. 테스트 종류 및 목적

### 4.1 CI 테스트 (정적 검증)

**목적**

* 상대시간 계산 로직 및 UI가 의도대로 동작하는지 검증

**특징**

* Date.now()를 고정(mock)하여 실행
* 실행 시점에 관계없이 항상 동일한 결과 보장

**검증 항목**

1. data-crawled-at 속성이 존재하는가
2. 상대시간 문자열이 timestamp와 논리적으로 일치하는가
3. UI 포맷이 깨지지 않았는가

---

### 4.2 모니터링 테스트 (동적 검증)

**목적**

* 운영 환경에서 데이터가 실제로 주기적으로 갱신되고 있는지 감시

**특징**

* 실제 Date.now() 기준으로 실행
* 상대시간 문자열의 정확한 값은 검증하지 않음

**검증 항목**

1. data-crawled-at 값이 현재 시각보다 과거인가
2. 현재 시각과의 차이가 허용 임계값 이내인가
3. 상대시간 문자열이 diff 범위에 맞는 단위를 사용하는가

---

## 5. 모니터링 테스트 검증 기준

### 5.1 시간 차이 검증

```text
now - data-crawled-at <= MAX_DELAY
```

* MAX_DELAY 기본값: 1시간
* 서비스 특성에 따라 조정 가능

### 5.2 이상 상태 판단 기준

| 조건                 | 상태       |
| ------------------ | -------- |
| diff <= MAX_DELAY  | 정상       |
| diff > MAX_DELAY   | 경고 또는 실패 |
| data-crawled-at 누락 | 실패       |

---

## 6. Playwright 테스트 구현 요구사항

### 6.1 테스트 구조 분리

Playwright 테스트는 목적에 따라 분리한다.

```text
tests/
 ├─ ci/
 │   └─ relative-time.spec.ts
 └─ monitoring/
     └─ crawl-latency.spec.ts
```

또는 태그 기반 분리도 허용한다.

```ts
test.describe('@monitoring', () => { ... })
```

---

### 6.2 실행 방식

| 구분       | 실행 방식                                    |
| -------- | ---------------------------------------- |
| CI 테스트   | npx playwright test --project=ci         |
| 모니터링 테스트 | npx playwright test --project=monitoring |

---

## 7. 주기적 실행 요구사항

### 7.1 실행 스케줄 요구사항

본 테스트는 **GitHub Actions의 schedule(cron)** 을 사용하여 주기적으로 실행한다. 다만, 운영 상황에 따라 실행 시간과 기간이 자주 변경될 수 있으므로 **시간 관련 설정은 코드 수정 없이 환경 변수 기반으로 관리**되어야 한다.

#### 7.1.1 기본 실행 조건

* 실행 요일: 월 ~ 금 (토, 일 제외)
* 실행 시간: 10:00 ~ 17:00 (KST)
* 실행 기간: 특정 시작일로부터 4일간

#### 7.1.2 가변 스케줄 설계 요구사항

* 실행 시간, 요일, 기간은 GitHub Actions 환경 변수로 제어 가능해야 한다.

* 예시 환경 변수

    * MONITOR_START_DATE (YYYY-MM-DD)
    * MONITOR_END_DATE (YYYY-MM-DD)
    * MONITOR_START_HOUR (예: 10)
    * MONITOR_END_HOUR (예: 17)
    * MONITOR_TIMEZONE (기본값: Asia/Seoul)

* cron 자체는 비교적 촘촘하게 설정하되, **실제 실행 여부는 workflow 내부 로직에서 판단**한다.

* 조건에 부합하지 않는 경우 테스트는 즉시 종료(success)되어야 한다.

---

### 7.2 실행 방식

* GitHub Actions `schedule` 트리거 사용
* 권장 cron 예시 (10분 단위)

```text
*/10 * * * *
```

* 실행 시 현재 시각이 설정된 기간/시간 범위에 포함되는지 확인 후 테스트 수행

---

## 8. 알림 시스템 요구사항

### 8.1 알림 채널

* Discord Webhook을 이용한 알림 전송을 지원해야 한다.
* Webhook URL은 GitHub Secrets 또는 환경 변수로 관리한다.

---

### 8.2 알림 중요도(Level)

테스트 실패 유형에 따라 알림 중요도를 구분한다.

| 중요도      | 설명                  |
| -------- | ------------------- |
| INFO     | 일시적 문제, 재시도 가능 상태   |
| WARNING  | 지연 또는 비정상 상태 감지     |
| CRITICAL | 데이터 미갱신, 시스템 장애 가능성 |

---

### 8.3 알림 집계(Aggregation) 요구사항

* 동일 실행 주기 내 여러 문제가 발생한 경우 **알림은 1회로 집계하여 전송**해야 한다.
* 알림 메시지에는 다음 정보가 포함되어야 한다.

    * 발생 시각
    * 문제 유형 목록
    * 각 문제의 중요도
    * 영향받은 row 또는 대상 식별자

---

### 8.4 알림 모듈 분리 요구사항

* 알림 로직은 테스트 로직과 분리된 모듈로 설계한다.
* 테스트 코드에서는 결과를 구조화된 형태로 반환한다.
* 알림 모듈은 결과를 해석하여 Discord 메시지를 생성한다.

---

## 9. SSE(Server-Sent Events) 연결 상태 간접 검증 요구사항

### 9.1 검증 접근 방식에 대한 판단

본 시스템에서는 SSE 연결 상태를 **직접 감지(onopen/onerror)** 하기보다는,
**SSE를 통해 전달되는 데이터의 결과물(시간 데이터 갱신 여부)** 을 기준으로 간접 판단하는 방식을 기본 전략으로 채택한다.

이는 다음 이유로 더 효율적이고 안정적인 접근으로 판단된다.

* 실제 목적은 "SSE가 연결되었는지"가 아니라 "데이터가 정상적으로 갱신되고 있는지"이다.
* SSE 연결은 성공했으나 이벤트가 오지 않는 경우도 실질적인 장애 상태이다.
* 브라우저/네트워크 환경에 따라 SSE 연결 이벤트 자체는 flaky 할 수 있다.
* UI에 노출되는 시간 데이터는 사용자 관점의 최종 결과물이므로, 운영 관점에서 더 의미 있는 지표이다.

---

### 9.2 간접 검증 기준

SSE 연결 상태는 다음 조건을 통해 간접적으로 판단한다.

1. 페이지 진입 이후
2. 일정 시간 내(data 갱신 허용 시간)
3. 하나 이상의 row에서 `data-crawled-at` 값이 갱신되었는지 여부

---

### 9.3 이상 상태 판단 기준 (간접)

| 조건                         | 판단                  | 중요도      |
| -------------------------- | ------------------- | -------- |
| data-crawled-at이 주기적으로 갱신됨 | 정상                  | -        |
| 갱신 지연 (임계시간 초과)            | SSE 또는 백엔드 지연 의심    | WARNING  |
| 일정 시간 동안 갱신 없음             | SSE 연결 실패 또는 시스템 장애 | CRITICAL |

---

### 9.4 직접 SSE 검증의 위치

* SSE 연결 이벤트(onopen/onerror)에 대한 직접 검증은 **보조 수단(optional)** 으로 취급한다.
* 디버깅 또는 장애 원인 분석용 테스트에서만 사용 가능하다.
* 운영 모니터링 테스트의 성공/실패 기준에는 포함하지 않는다.

---

### 9.2 검증 항목

* 페이지 진입 후 일정 시간 내 SSE 연결이 수립되는지 여부
* SSE 연결 이후 이벤트가 정상적으로 수신되는지 여부

---

### 9.3 이상 상태 판단 기준

| 상황                   | 중요도      |
| -------------------- | -------- |
| SSE 연결 지연 (일정 시간 초과) | WARNING  |
| SSE 연결 실패            | CRITICAL |
| SSE 연결 후 이벤트 미수신     | WARNING  |

---

## 10. 비기능 요구사항

* 테스트는 flaky 하지 않아야 한다.
* 네트워크 지연에 의한 오탐(false positive)을 최소화한다.
* 테스트 실행 시간은 1분 이내를 권장한다.

---

## 11. 향후 확장 고려사항

* 알림 중요도별 Discord 채널 분리
* 알림 빈도 제한(Rate limit) 적용
* SSE 상태와 크롤링 지연의 상관관계 분석
* API 헬스체크와 UI 모니터링 결과 통합

---

## 12. 요약

본 테스트는 다음 원칙을 따른다.

* 시간 기반 조건은 **설정으로 제어**한다.
* 상대시간 UI는 참고용이며, 판단 기준은 절대시간이다.
* 알림은 **중요도 기반 + 집계 방식**으로 전달한다.
* 실시간 연결(SSE) 실패 또한 운영 장애 신호로 취급한다.

이를 통해 Playwright 기반 테스트를 단순 E2E를 넘어 **운영 모니터링 도구**로 활용할 수 있다.

본 테스트는 **상대시간 UI를 신뢰하지 않고**,
**절대시간(data-crawled-at)을 기준으로 시스템 상태를 검증**하는 것을 원칙으로 한다.

이를 통해 UI 테스트와 운영 모니터링을 동일한 Playwright 인프라 위에서 안정적으로 운영할 수 있다.
